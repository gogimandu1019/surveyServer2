### 왜 이렇게 했나
- **테스트를 먼저 만든 이유**: 테스트가 없으면 리팩터링하고 나서 "전과 똑같이 동작하는지" 확인할 방법이 없기 때문입니다. 그래서 내부 구조와 상관없이 HTTP로만 확인하는 테스트를 만들어, 리팩터링 전과 후에 똑같이 돌릴 수 있게 했습니다.
- **API를 그대로 둔 이유**: 화면(`static/*.html`)이 지금 API 모양에 맞춰져 있어서, API를 바꾸면 화면과 테스트를 모두 고쳐야 하기 때문입니다. 서버 내부만 먼저 정리하고, API 변경은 나중에 따로 하기로 했습니다(2026-11-05 결정, [결정-기록.md](결정-기록.md)).
- **버그도 그대로 둔 이유**: 리팩터링과 버그 수정을 한 번에 하면, 테스트가 깨졌을 때 실수 때문인지 의도한 변경 때문인지 구분할 수 없기 때문입니다.

아래는 PR을 올릴 때 그대로 쓰려고 준비한 본문과 리뷰 코멘트입니다.

## PR 설명

### 무엇을 바꿨나
`server.py`의 **내부만** 다시 짰습니다. 밖에서 보이는 것은 그대로입니다.

- URL과 JSON 응답 모양: `/api/getSurvey?code=`, `/api/adminProc`의 `cmd`, 실패해도 HTTP 200 + `{"result":"FAIL"}` 등
- DB 스키마(`survey.db`를 그대로 씀)
- `static/*.html`(손대지 않음)

### 일부러 그대로 둔 것 (동작 변경 없음 원칙)
`tests/test_known_quirks.py`가 고정하고 있는 레거시 동작은 고치지 않았습니다. 코드에 `레거시 동작 그대로`라고 주석을 달아 두었고, 고치려면 별도 PR에서 테스트와 함께 바꾸면 됩니다.

- 점수에 `"²"`를 보내면 500 + 예외 메시지 노출
- `2026-1-5` 날짜를 정규화하지 않고 저장
- 50만 바이트가 넘는 본문을 에러 없이 무시
- CSV 인젝션 처리 없음
- 쿼리스트링을 URL 디코딩하지 않음
- 중복 응답을 쿠키로만 막음

### 확인한 것
- **특성 테스트**: `python3 tests/run.py` → 53개 모두 통과(3회 연속). 리팩터링 전에 레거시 코드로 만든 테스트입니다.
- **실제 데이터로 비교**: `survey.db` 복사본에 옛 서버와 새 서버를 각각 띄우고, 같은 GET 요청 17개(목록, 설문 3개의 조회·결과·CSV, 관리 목록·조회, 화면, 404)의 응답을 비교했습니다. 서로 다른 건 `localBase`의 포트 번호뿐이었고, 이는 두 서버를 다른 포트로 띄웠기 때문입니다.
- **브라우저**: 새 서버로 관리 목록, 설문, 결과, 설문 편집 화면을 열어 정상 표시와 콘솔 에러 없음을 확인했습니다. 서버 로그에는 접속 IP가 남지 않습니다. 실제 DB를 쓰는 화면이라 응답 제출이나 관리 버튼은 누르지 않았습니다(이 동작들은 특성 테스트가 다룹니다).

### 동작이 달라질 수 있는 곳 (테스트 밖)
- **잘못된 HTTP 요청**(요청 줄이 깨진 경우 등): 전에는 500과 예외 메시지, 이제는 `http.server`가 400을 돌려줍니다.
- **응답 헤더**: `Server`, `Date` 헤더가 추가됩니다. 상태 문구도 정확해집니다(예: 전에는 400·409 등이 모두 "OK"로 나갔음).
- **DB 연결**: 화면 파일 요청에서는 DB를 열지 않습니다.
- **설문 코드 생성**: 예측 가능한 `random` 대신 `secrets`를 씁니다. 형식(소문자·숫자 7자)은 같습니다.

## 리뷰 코멘트

**`server.py:32` — `SHOW_ERROR_DETAILS = True`**
레거시와 같이 500 응답 본문에 예외 메시지를 넣습니다. 전에는 주석이 "운영에서는 0으로"라고 하고 실제로는 1이었는데, 그 거짓 주석을 없애고 왜 켜 두는지 적었습니다. 수업용 와이파이에 열어 둘 때는 끄는 것이 맞지만, 끄면 `test_superscript_digit_rating_is_500`이 깨지므로 별도 PR로 분리합니다.

**`server.py:35-45` — 매직넘버를 이름 있는 상수로**
`600000`, `500000`, `31536000`, `5000`, `300` 같은 숫자를 상수로 모았습니다. `COOKIE_MAX_AGE_SEC = 365 * 24 * 60 * 60`이라서, "1달"이라던 주석과 달리 실제로는 1년이라는 게 코드에서 바로 보입니다.

**`server.py:119` — `query_param()`**
쿼리 파싱 복붙 5곳을 하나로 합쳤습니다. `kv[5:]`, `kv[3:]`처럼 이름 길이를 하드코딩하던 것도 `len(name) + 1`로 바꿨습니다. URL 디코딩을 하지 않는 것은 레거시 동작이라 그대로 두었습니다(`test_query_param_is_not_url_decoded`).

**`server.py:144` — `PRAGMA foreign_keys = ON`**
스키마에 `ON DELETE CASCADE`가 선언돼 있었는데 이 PRAGMA가 꺼져 있어서, 레거시는 `answers` → `responses` → `surveys` 순서로 손으로 지웠습니다. 이제 `cmd_reset`과 `cmd_delete`(632, 636줄)가 한 줄씩입니다. 기존 `survey.db`도 같은 스키마로 만들어져 있어서 그대로 동작합니다.

**`server.py:174` — `new_slug()`**
슬러그 생성 복붙 3곳(예시 데이터, 신규, 복사)을 합쳤습니다. `random` 대신 `secrets`를 써서 설문 코드를 추측하기 어렵게 했습니다.

**`server.py:202` — `clean_survey_input()` / `clean_question()`**
신규와 수정에 50줄씩 복붙돼 있던 검증을 하나로 합쳤습니다. 에러 메시지와 검사 순서는 글자 하나까지 같습니다(`test_validation_messages_for_new_and_update`가 신규·수정 양쪽을 모두 확인).

**`server.py:249` — `clean_answers()`**
타입마다 반복되던 "빈 값이면 필수 체크" 블록을 위로 올려 한 번만 합니다. 실패는 `Fail` 예외로 바로 끝내고, 전에 쓰던 `sErr` 플래그와 `break`는 없앴습니다.

**`server.py:284-285` — 점수 검사**
`"²"`가 500이 되는 버그를 **알고도 그대로 둔** 곳이라 주석을 달았습니다. 고칠 때는 `value.isdigit()`을 `value.isascii() and value.isdigit()`로 바꾸고 quirks 테스트를 갱신하면 됩니다.

**`server.py:353` — `ORDER BY RANDOM()`**
레거시 주석은 "최신순"이라고 했지만 실제로는 무작위였습니다. 코드는 그대로 두고 주석을 사실대로 고쳤습니다. 무작위인 이유는 응답 순서로 누가 썼는지 짐작하지 못하게 하려는 것입니다.

**`server.py:358-369` — `export_csv()`**
CSV를 손으로 이어 붙이던 것을 `csv.writer(quoting=QUOTE_NONNUMERIC)`로 바꿨습니다. 출력은 글자 단위로 같습니다: 번호만 따옴표 없음, 나머지는 따옴표, `\r\n`, BOM(`test_csv`). 소스에 직접 박혀 있던 보이지 않는 BOM 문자는 `"﻿"`로 바꿔 눈에 보이게 했습니다. 365줄의 `a.rowid`는 한 응답 안의 답 순서를 명시적으로 고정하려고 넣었습니다(레거시는 인덱스 순서에 우연히 기대고 있었음).

**`server.py:415-424` — `SurveyServer`**
`request_queue_size`를 레거시의 `listen(100)`과 맞췄습니다. 기본값 5로 두면 수업 중에 접속이 몰릴 때 연결이 거부될 수 있습니다. `handle_error`를 바꾼 이유는, 기본 구현이 오류가 나면 **접속 IP를 stderr에 찍기** 때문입니다(익명성).

**`server.py:428` — `protocol_version = "HTTP/1.0"`**
레거시처럼 요청 하나에 연결 하나로 처리하고, 응답마다 `Connection: close`를 보냅니다. keep-alive는 이번 PR 범위 밖입니다.

**`server.py:447` — `read_body()`**
50만 바이트가 넘으면 본문을 **읽지 않고 버립니다**(레거시 동작, `test_oversized_body_is_silently_ignored`). `Content-Length`가 0 이하일 때도 읽지 않게 막았습니다. 레거시 그대로 `rfile.read(-5)`를 하면 연결이 끝날 때까지 멈춥니다.

**`server.py:454` — `route()`**
DB 연결을 API 요청에서만 엽니다. `Fail`이면 커밋하지 않고, 어떤 경우든 `finally`에서 닫습니다. 레거시는 화면 파일 요청에도 DB를 열었습니다.

**`server.py:492` — `log_request()` / `log_message()`**
`http.server` 기본 로그는 접속 IP를 찍기 때문에 덮어썼습니다. 쿼리스트링(설문 코드)도 남기지 않고 경로만 남깁니다.

**`server.py:519` — `is_admin_write_allowed()`**
레거시 주석은 "jQuery 쓸때 넣은거"라서 지워도 될 것처럼 보였는데, 실제로는 CSRF 방어입니다. 주석으로 분명히 했습니다. Origin 정규식은 레거시와 똑같이 `re.match`를 씁니다.

**`server.py:570` — `api_admin_list()`**
설문마다 응답 수를 따로 세던 N+1 쿼리를 서브쿼리 하나로 바꿨습니다. LAN IP는 시작할 때 한 번 구해 `server.lan_ip`에 둡니다(전역 변수 제거).

**`server.py:588` — `api_admin_proc()`**
`cmd` 하나로 분기하는 단일 엔드포인트는 화면이 그렇게 호출하므로 유지했습니다. 대신 분기는 `ADMIN_COMMANDS` 표로 옮겼습니다. `cmd`가 문자열이 아닐 때(예: 리스트) 500 대신 "알 수 없는 명령"이 나오도록 `isinstance` 검사를 넣었는데, 레거시도 이 경우 같은 메시지였습니다.

**`server.py:605` — `cmd_new()`**
레거시 주석 "신규는 바로 오픈"은 사실이 아니었습니다(마감 상태로 생성). 동작은 그대로 두고 주석을 사실대로 고쳤습니다.

**`server.py:641` — `main()`**
모듈을 import만 해도 DB가 생기고 포트를 잡던 문제를 없앴습니다. 이제 다음 단계로 함수 단위 테스트를 붙일 수 있습니다.
